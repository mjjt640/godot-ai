# 模块构筑型幸存者项目架构约束清单

## 文档目的

这份文档不是描述一个“理想但很重”的大架构，而是给当前项目规定一组长期有效的约束，确保项目在加入模块、敌人、升级、UI、平衡调整和 AI 辅助修改后，仍然保持清楚、可改、可追踪。

适用范围：

- 当前 Godot 项目
- 模块构筑型幸存者玩法
- AI 辅助开发流程

这份文档优先解决 4 个问题：

- 当前状态到底归谁管
- 静态数据到底怎么存、怎么改
- 主调用链怎么保持单一且可追踪
- AI 改代码时什么能动，什么不能乱动

## 一、核心原则

如果后面只记得几条规则，优先记这些：

- 静态配置和运行时状态必须分开
- 当前 build 必须有唯一真相来源
- 武器行为必须收口到统一的结算边界
- UI 只展示状态，不重算玩法规则
- 新功能优先扩展现有系统，不轻易平行新建第二套系统
- AI 可以加速实现，但不能替项目擅自扩大抽象层

## 二、状态归属约束

这一类项目最先要定清楚的，不是目录，而是`谁拥有最终状态`。

### 1. 静态配置

静态配置描述“默认是什么”，例如：

- 武器基础参数
- 模块定义
- 升级定义
- 敌人基础配置

静态配置不能保存这些内容：

- 本局实时变化
- 玩家当前 build
- 当前经验、血量、冷却
- 运行中临时增伤或 Buff

### 2. 运行时状态

运行时状态必须保存在运行中的对象里，例如：

- 玩家当前血量
- 当前经验值
- 当前已安装模块
- 当前 build 推导后的实际武器行为
- 敌人的目标、位置、受击状态

禁止把运行时状态写回静态配置资源。

### 3. 当前 Build 的唯一来源

当前 build 必须有唯一真相来源。

建议：

- `build_state.gd` 负责保存当前模块选择
- `module_applier.gd` 负责把当前模块选择结算成武器行为
- `weapon_controller.gd` 只消费结算结果，不重新解释模块

禁止出现这些情况：

- UI 自己推导 build 结果
- 子弹脚本直接读取模块资源并临时判断行为
- 升级系统直接改多个战斗脚本里的局部变量

## 三、静态数据存放策略

这一部分是当前项目后续平衡调整最关键的约束。

目标不是“能存起来”，而是：

- 数据和代码清楚分离
- 后期调数值时改动集中
- 结构清楚，AI 不容易乱加字段
- 与 Godot 编辑器工作流兼容

### 1. 当前主方案

当前项目的核心静态数据，主方案应使用 `Godot Resource`。

原因：

- 它是 Godot 原生数据方案
- 类型边界比通用文本配置更明确
- 与场景、脚本、导出字段的协作更自然
- 更适合做后续 AI 辅助修改时的结构约束

适合放进 `Resource` 的内容：

- 武器静态参数
- 模块定义
- 敌人静态参数
- 升级选项定义

### 2. 暂不采用的主方案

当前阶段不应把以下方案作为核心静态平衡数据的主载体：

- `JSON`
- 数据库

原因不是它们不能用，而是它们在当前阶段会引入额外复杂度，并削弱 Godot 编辑流程和结构约束。

`JSON` 当前更适合：

- 存档
- 数据交换
- 简单导入导出

数据库当前更适合未来这些场景：

- 大量结构化查询
- 外部内容管理工具
- 联机后端
- 复杂编辑器外数据系统

在原型和首个可玩版本阶段，不要为了“以后可能会大”提前上数据库。

### 3. 静态数据文件组织规则

静态数据应该保持：

- 分类明确
- 单条可定位
- 单次改动影响范围小

建议规则：

- 一类数据一个目录
- 一条记录一个资源文件
- 不把大量配置挤进一个超大总表文件

这样做的好处：

- 平衡调整定位更直接
- Git diff 更容易看
- AI 修改单条数据时更安全
- 不同数据类别的字段边界更容易稳定

### 4. 数据结构稳定性规则

静态数据要可调，不等于字段可以随意扩张。

必须遵守：

- 每类数据有清晰固定的字段职责
- 相同含义的数据不能在多个类里重复定义
- 能用明确字段表达的内容，不要全塞进自由字典

允许保留少量可扩展字段。

但禁止出现这些情况：

- 同一个伤害来源同时在多个数据对象里定义
- 同一显示文本在多个地方重复写
- 同一模块行为既靠字段表达，又靠多个脚本私下补逻辑

### 5. 文本与数值分离

玩家可见文本不要直接写死在逻辑代码里，也不要把显示文本和行为规则混在一起。

建议：

- 静态配置存显示 key 或清晰的展示字段
- 实际显示文本通过统一文本入口处理

这样后面改文案、多语言或统一 UI 表达时，不需要反复碰战斗逻辑。

### 6. 平衡调整友好性规则

为了后期平衡更容易做，静态数据应该满足：

- 常改的数值集中在少数明确字段中
- 一次调整不需要跨多个脚本同步修改
- 同一种平衡参数只有一个可信来源

如果某个平衡项需要同时改：

- 模块数据
- 武器脚本
- 子弹脚本
- UI 描述脚本

说明当前数据设计已经不够干净。

### 7. 未来扩展规则

如果后面静态数据量变大，允许增加一层“表格编辑源”，例如 `CSV`。

但规则必须是：

- `CSV` 作为平衡编辑源
- `Resource` 作为运行时正式读取格式

不要直接把项目核心玩法配置切成“运行时直接读 CSV”。

这样做的目的，是兼顾：

- 表格批量调数值的效率
- Godot 工程内部的结构清晰度

## 四、主调用链约束

本项目里最重要的不是“用了多少系统”，而是`主调用链必须稳定且可追踪`。

推荐的核心链路：

1. 玩家获得升级选项
2. 玩家选择一个升级
3. `upgrade_manager` 通知 `build_state`
4. `build_state` 更新当前模块槽位
5. `module_applier` 生成新的 `shot_profile`
6. `weapon_controller` 在下一次开火时读取新的 `shot_profile`
7. `projectile_controller` 按已结算结果执行

这个链路必须满足：

- 每一步职责单一
- 可以通过日志或调试输出来追踪
- 出错时能快速定位是哪一层改坏了数据

不建议的链路：

- 升级 UI 直接改武器脚本
- 子弹命中后反向修改 build 结构
- 多个系统同时维护“当前武器伤害”

## 五、系统边界约束

### 1. Gameplay 和 Presentation 分开

逻辑层负责：

- 伤害
- 冷却
- 模块结算
- 子弹数量
- 爆炸范围
- 穿透次数

表现层负责：

- 动画
- 飘字
- 音效
- 特效
- HUD
- 升级卡展示

允许表现层读取逻辑状态。

不允许表现层决定逻辑结果。

### 2. Glue Code 只协调，不承载核心规则

胶水层适合做这些事：

- 接收命中结果
- 把命中结果分发给生命、状态、表现系统
- 串起升级选择和 build 更新流程

胶水层不应该负责：

- 伤害公式
- 模块平衡逻辑
- 武器最终行为推导

如果某个 Glue 脚本开始包含大量 `if module_id == ...`，说明职责已经错位。

### 3. 避免平行系统

新增功能时优先问：

- 这个需求能不能扩展现有系统
- 还是必须新建系统

禁止轻易出现：

- 第二套升级系统
- 第二套模块解释器
- 第二套伤害入口
- 第二套静态数据访问方式

同一职责必须有单一入口。

## 六、文件职责约束

如果你想长期使用 AI 辅助开发，文件职责一定要稳定。

推荐的核心文件职责：

- `build_state.gd`：保存当前已选模块和已推导的 build 状态
- `module_applier.gd`：把基础武器和模块转换成 `shot_profile`
- `weapon_controller.gd`：负责开火节奏和发射
- `projectile_controller.gd`：负责飞行、命中、生命周期
- `hit_resolver.gd`：负责一次命中的规则结算
- `xp_manager.gd`：负责经验与升级触发
- `upgrade_manager.gd`：负责升级候选生成和应用结果
- `hud_controller.gd`：只显示运行时状态

一个文件如果开始同时处理：

- 配置读取
- 状态保存
- UI 更新
- 命中规则

就已经超出合理职责边界。

## 七、模块系统专用约束

这个项目不是通用战斗框架，而是模块构筑游戏，因此模块系统要遵守额外规则。

### 1. 槽位语义固定

每个槽位只负责一个明显维度。

不要让一个槽位同时承担多个抽象层面的变化。

### 2. 先做半数据驱动，不做万能系统

第一版允许：

- 模块数据放在 `Resource`
- 某些行为判断仍然写在 `module_applier.gd`
- 为少量模块类型写特化逻辑

第一版不追求：

- 任意模块可堆叠
- 任意模块可互相触发
- 任意行为都能通过纯配置拼出来

这是刻意限制，不是架构失败。

### 3. `shot_profile` 是关键边界

模块系统最终必须收口到一个明确的武器执行结果对象，例如 `shot_profile`。

它至少应该描述：

- 发射数量
- 发射角度
- 伤害
- 冷却
- 弹速
- 穿透次数
- 爆炸信息

只要 `shot_profile` 边界稳定，后面换表现、换模块内容、换平衡参数，都不会牵动整条战斗链。

## 八、执行顺序约束

这个项目的核心循环建议遵守：

1. 读取输入
2. 更新移动
3. 推进刷怪和运行流程
4. 处理武器开火
5. 处理子弹移动和命中
6. 结算伤害与死亡
7. 播放表现反馈
8. 更新 HUD

简单原则：

- 先产生事实
- 再结算规则
- 最后刷新表现

注意：

- 玩家移动、攻击冷却、子弹物理优先放在 `_physics_process()`
- 纯视觉插值和 UI 动画可以放在 `_process()`
- 升级弹窗类流程要明确暂停哪些系统，不要靠“刚好没更新”凑效果

## 九、性能与可替换性约束

当前阶段不要为了“以后可能卡”提前做复杂优化，但要提前留好替换接口。

建议提前独立边界的地方：

- `spawn_manager`
- `hit_resolver`
- `module_applier`
- 敌人目标选择逻辑
- 子弹生成与复用逻辑

当前性能优先级：

- 先保证主链路清楚
- 再保证对象数量可控
- 最后再做对象池、空间分区、分帧

不要在原型阶段过早引入复杂算法。

## 十、AI 辅助开发约束

这部分是本项目必须长期执行的规则。

### 1. 先读现有结构，再改代码

任何 AI 在新增或修改功能前，应先确认：

- 已有目录结构
- 已有核心脚本职责
- 现有数据来源
- 现有主调用链

### 2. 先扩展已有系统，再考虑新建文件

如果可以扩展现有 `build_state`、`module_applier`、`upgrade_manager`，就不要平行新建：

- `BuildManager`
- `WeaponAssembler`
- `CombatHelper`
- `UpgradeService`

除非现有文件职责已经明确不适合承载该功能。

### 3. 新增文件必须说清理由

新增文件时至少要能回答：

- 它负责什么
- 它不负责什么
- 为什么不能放进现有文件
- 它的输入输出是什么

### 4. AI 生成代码后必须验证四类事实

- 引擎 API 是否真实存在
- 节点路径和资源路径是否真实存在
- 数据流是否符合当前项目主链路
- 性能结论是否经过实际验证

### 5. 禁止 AI 自行扩大抽象层

如果当前只需要支持：

- 两个模块槽位
- 少量模块类别
- 单一基础武器

就不要让 AI 自作主张补：

- 通用事件总线
- 状态树
- 全局配置中心
- 一套未来模块工厂体系

## 十一、新增功能前的判断清单

每次要加新功能前，先问下面这些问题：

- 这个功能改的是静态配置，还是运行时状态
- 它应该挂到现有哪条主链路上
- 它会不会让 UI 开始拥有逻辑
- 它会不会让子弹重新理解模块
- 它能否通过扩展 `shot_profile` 解决
- 是否新增了第二个真相来源
- 是否新增了第二套静态数据入口
- 如果交给 AI，这个任务能否被收敛成 1 到 2 个职责明确的文件

如果这些问题答不清，先不要写代码。

## 十二、当前阶段的落地重点

对当前项目，最值得优先落实的不是大而全的框架，而是下面这些点：

1. 把 `build_state` 定成当前 build 的唯一来源
2. 把 `module_applier` 定成 build 到武器行为的唯一转换器
3. 把 `shot_profile` 定成战斗执行边界
4. 把静态平衡数据统一收口到 `Resource`
5. 把升级流程固定成可追踪主链路

这几个点稳住后，后面再加敌人、模块、UI、特效、平衡，项目都还能继续长。

## 最终结论

这类项目真正的架构目标不是“看起来高级”，而是：

- 当前能做
- 后面还能改
- 以后交给 AI 继续接手也不容易歪

如果只能记一条，就记这句：

`模块系统的真相来源要唯一，静态平衡数据要集中且易改，武器行为的结算边界要收口，AI 的改动范围要受控。`
